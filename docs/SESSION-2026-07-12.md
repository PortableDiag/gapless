## 1. What the session set out to answer

> "Does the player save the shuffle and repeat state on restart?"

**Yes — and it already did.** `state.json` carried `shuffle` and `repeat`, they
were restored at startup, and two unit tests already covered the round trip.

But the audit turned up a real hole next to it, which is what the session fixed.

## 2. The bug that was found and fixed

**Shuffle/repeat changed over MPRIS were not persisted and did not repaint the UI.**

Repeat and shuffle are unlike every other control in the app: they **move no
pipeline**. Play, pause, next, seek all push the GStreamer pipeline, and the
pipeline's bus messages are what drive the UI. Repeat and shuffle just flip a
flag on the `Player`, so there was nothing to drive the UI off.

The GTK button handlers papered over this by doing the extra work by hand
(repaint the icon, call `schedule_save`). The MPRIS handlers — `SetProperty` on
`Shuffle` / `LoopStatus`, i.e. a lock-screen widget or `playerctl` — did not:

- the in-app button kept showing the **old** state, and
- **no save was scheduled**, so the change was lost unless the window was closed
  cleanly (the close handler re-reads the `Player` on its way out and saved it
  as a side effect).

### The fix — one event, one handler

Instead of duplicating the button handlers' extra work into the MPRIS handlers,
mode changes now emit an event, and **both entry points flow through it**:

| File | Change |
|---|---|
| `src/player.rs` | New `PlayerEvent::ModesChanged { repeat, shuffle }`. Emitted by `set_repeat` and `set_shuffle` via a new private `emit_modes`. Both setters now take their lock, mutate, read back the *other* field, drop the lock, then emit. |
| `src/main.rs` | `listen_for_events` handles `ModesChanged`: `set_repeat_look` + `set_shuffle_look`, `mpris::publish_modes`, `schedule_save`. The two button handlers were **reduced to one line each** — they just set the mode and let the event do the rest. |
| `src/mpris.rs` | **No functional change.** Its handlers already call `player.set_repeat` / `set_shuffle`, which now emit. Only a comment explaining why these two differ from the transport controls. |

Committed as `ffdc8d6`, merged fast-forward to `main`, pushed to `origin`.

### Two things to know before touching this code again

- **No D-Bus feedback loop.** The `ModesChanged` handler calls
  `mpris::publish_modes`, which calls `mpris.set_shuffle()` — that updates the
  *server's* property and emits `PropertiesChanged`. It does **not** re-invoke
  `connect_set_shuffle`, which only fires on an inbound D-Bus `Set`. So the echo
  back to MPRIS is safe and is what lets a *second* MPRIS client see a change it
  did not originate.
- **`try_send`, not `send_blocking`.** The setters are called on the GTK main
  thread. The channel is unbounded so neither can block, but `send_blocking` on
  the main thread is a smell; a closed channel just means shutdown.

## 3. How it was verified — `scripts/verify-mpris-modes.sh`

The unit tests could not have caught this bug: they test the `Settings` struct's
serde round trip, and the bug was that *nothing ever called save*. So the check
is end-to-end.

```sh
./scripts/verify-mpris-modes.sh
```

The script, and **why each awkward part of it is load-bearing**:

1. **Seeds the opposite state** (`repeat: "off"`, `shuffle: false`) so a pass
   cannot be a no-op.
2. **Sets the modes only over D-Bus** — `org.freedesktop.DBus.Properties.Set` on
   `Shuffle` and `LoopStatus`. The GUI is never touched.
3. **`SIGKILL`s the app.** This must stay a `kill -9`. Closing the window would
   let `persist_on_close` run and re-save the state on the way out, which is
   exactly what used to mask the bug. A hard kill is the only way to prove the
   *debounced* save actually fired.
4. **Private `dbus-run-session` + private `XDG_CONFIG_HOME`.** A copy of Gapless
   running on the real desktop already owns `org.mpris.MediaPlayer2.Gapless` on
   the session bus — without isolation the script would silently drive *that*
   instance and scribble on the real `~/.config/gapless/state.json`.

Result:

```
seeded:                 repeat=off    shuffle=False
set via MPRIS:          LoopStatus=Track  Shuffle=true
on disk after SIGKILL:  repeat=one    shuffle=True
[PASS] MPRIS-only mode change was persisted without a clean close
```

That result also proves the **icon repaint**: the repaint and the save live in
the same `ModesChanged` handler body, so the save landing means the handler ran.

## 4. The MPRIS surface (this app's closest thing to an API)

Bus name `org.mpris.MediaPlayer2.Gapless`, object `/org/mpris/MediaPlayer2`,
interface `org.mpris.MediaPlayer2.Player`. All of it lives on the **GTK main
thread** — `mpris-server`'s `Player` is `Rc<LocalServer>` and takes plain `Fn`
callbacks, so there is no cross-thread command channel.

| Member | Direction | Notes |
|---|---|---|
| `Play` `Pause` `PlayPause` `Stop` `Next` `Previous` | in | `PlayPause` on a fresh launch starts the queue rather than resuming an empty pipeline |
| `Seek` | in | **relative** offset, may be negative |
| `SetPosition` | in | absolute |
| `Shuffle`, `LoopStatus` | in + out | **the subject of this session's fix** |
| `Volume` | in + out | |
| `Metadata`, `PlaybackStatus`, `Position` | out | `publish_track`, `publish_status`, `publish_position` |

Read it live with:

```sh
gdbus call --session --dest org.mpris.MediaPlayer2.Gapless \
  --object-path /org/mpris/MediaPlayer2 \
  --method org.freedesktop.DBus.Properties.GetAll org.mpris.MediaPlayer2.Player
```

## 5. Build / install / run facts worth not rediscovering

- **The target dir is not `./target`.** `.cargo/config.toml` redirects it to
  `~/.cache/cargo-target/gapless/`. `./target/debug/gapless` does not exist and
  running it fails with exit 127.
- `scripts/install.sh` builds **release** and installs to `~/.local/bin/gapless`,
  plus the icon and `.desktop` entry. It does **not** need sudo.
- **Overwriting the binary does not update a running instance.** After
  installing, the old process keeps executing the old code until it is quit and
  relaunched.
- The desktop instance owns the MPRIS bus name. Any test that talks to
  `org.mpris.MediaPlayer2.Gapless` on the real session bus will hit *it*, not
  your build. Isolate with `dbus-run-session`.

## 6. Settings persistence — how it actually works

`~/.config/gapless/state.json`, written by `Settings::save` (`src/settings.rs`).

- `current_settings()` in `main.rs` builds the struct by **reading the live
  `Player`**, starting from `Settings::load()` so unknown/unmanaged fields
  survive.
- `schedule_save()` is **debounced by 600 ms** (`SAVE_DEBOUNCE`) — a volume drag
  would otherwise rewrite the file once per frame.
- Position is saved at most every 5 s while playing (`POSITION_SAVE_EVERY`), on
  pause, and on close.
- The resume point is stored as a **path, not an index**, because a rescan or an
  edited playlist renumbers the queue.
- `#[serde(default)]` on the struct: an older config must still load and keep
  what it does carry. There is a unit test for exactly this
  (`old_config_still_loads`).

## 7. OPEN BUG — crossfade does not audibly apply in the app

Reported at the end of the session, **not yet fixed**. Everything known:

**Symptom.** With a crossfade configured, tracks do not audibly crossfade in the
running app. Reported after a restart, with the setting unchanged in the UI.

**It is not a save bug.** The value is on disk:

```json
"crossfade_secs": 4.039087946,
"trim_silence": true,
"shuffle": true,
"repeat": "all"
```

**It is not the engine either.** The real engine, rendered through
`examples/capture` (the actual `Player` and mixer timeline, only the sink
swapped for a WAV writer), crossfades correctly — including with trimming on,
which was the first suspicion:

| Render (two 10 s tracks) | Result |
|---|---|
| no crossfade, no trim | 20.000 s — baseline |
| `GAPLESS_CROSSFADE=4` | **16.000 s** — correct 4 s overlap |
| `GAPLESS_CROSSFADE=4 GAPLESS_TRIM=1` | **16.000 s** — trim does **not** break crossfade |

So the fault is **app-side**: the value is saved, and the engine honours it when
it is set — meaning it is most likely not reaching the `Player` in the app's
particular startup/resume path, or is being undone by it.

**Leading hypothesis — the resume path.** The restart resumed mid-track
(`last_position_secs: 227`). `Player::seek` deliberately **rebuilds the
timeline** with the current track at its head; its own doc comment says this is
because the pad offsets "would not be [correct] if we seeked a timeline that
already had a crossfade scheduled into it" (`src/player.rs:509`). The resume
path lands in `start_at(track, offset)`. A follower scheduled after a `start_at`
with a non-zero skip is where to look first.

**Negative result — do not repeat this experiment as-is.** The obvious check
(`GAPLESS_SEEK=5 GAPLESS_CROSSFADE=4` through `examples/capture`, expecting
11 s) is **inconclusive**: the seek does not engage in a two-track capture. It
rendered 20.000 s / 16.000 s — byte-identical to the *no-seek* runs, i.e. the
harness ignored the seek. `GAPLESS_SEEK` is documented against a single-file
sweep render. Either fix the harness to honour a seek in a multi-track queue, or
reproduce in the GUI.

**Next question to settle first** (cheapest discriminator): does it crossfade
when playing straight through **without** a resume — e.g. after pressing Next?

- If yes → the bug is in the **resume/seek** path.
- If no → crossfade is not reaching the `Player` in the GUI **at all**, and the
  place to look is `build_prefs` / the startup restore order in `main.rs:250-268`.

Note while you are in there: `xfade_scale` is a `gtk::Scale` with a **0.5 step**,
and GTK rounds a scale's value to the step's digits — which is why a saved
4.039 s reads back as 4.0 in the UI. Cosmetic, not the bug, but it will waste
your time if you go hunting for the missing 39 ms.
